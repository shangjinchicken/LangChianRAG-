# 注释检查技能

## 技能说明

本技能用于检查「RAG 企业级知识库问答系统」项目的代码注释质量，从三个维度逐文件审查，发现问题并给出修改建议。

---

## 执行流程

### 第一步：确定检查范围

询问用户想检查哪些文件：
- **指定文件**：用户给出具体文件路径
- **指定目录**：例如 `backend/app/rag/`、`backend/app/services/` 下所有 `.py` 文件
- **全部改动**：当前分支相比 main 有改动的文件（`git diff --name-only main`）
- **全项目**：所有 `.py`、`.ts`、`.vue` 文件

### 第二步：逐文件检查（三个维度）

对每个文件，按以下三个维度逐一审查：

---

#### 维度一：注释覆盖率 📏

**标准**：每 10 行代码中，至少要有 3 行注释（即注释率 ≥ 30%）。

**检查点**：
- 每个函数/方法前面是否有注释说明"这个函数做什么"？
- 函数内部的复杂逻辑、关键步骤是否有行内注释？
- 变量名如果不够直观，是否有注释解释含义？
- 条件分支（if/else）、循环是否有注释说明"什么情况下走这个分支"？

**统计方法**：
- 注释行 = `#` 开头的行 + `"""..."""` docstring 行（Python）；`//`、`/* */`、`/** */`（TypeScript）；`<!-- -->`（Vue 模板）
- 代码行 = 非空行、非纯注释行
- 注释率 = 注释行 ÷ (注释行 + 代码行) × 100%

---

#### 维度二：注释准确性 ✅

**标准**：注释描述的内容必须和代码实际行为一致。

**检查点**：
- 注释说的"做什么"和代码真正执行的逻辑是否匹配？
- 注释中的参数名、变量名是否和代码中一致？
- 注释描述的业务规则是否和代码实现一致（比如检索 Top-K、模型名、分块大小）？
- 有没有"僵尸注释"——代码已经改了但注释没跟着改？
- 有没有"复读机注释"——只把代码翻译成中文，没有额外信息价值？

**判定示例**：
```python
❌ 不准确：
# 取 Top-10 结果
docs = results[:5]   # 实际是 Top-5，注释说反了

❌ 复读机注释（没有价值）：
# 把 name 设置为 username
self.name = username

✅ 好的注释：
# 混合检索返回 (文档, 分数)，这里取 RRF 融合后分数最高的 5 条作为上下文
docs = results[:5]
```

---

#### 维度三：小白可读性 👶

**标准**：注释用通俗易懂的中文书写，编程零基础的人也能看懂。

**检查点**：
- 是否避免了专业术语堆砌？如果用了术语，有没有解释？
- 是否解释了"为什么这么做"而不仅仅是"做了什么"？
- 涉及业务逻辑（RAG 检索、向量化、流式输出）是否有详细说明？
- 复杂的技术操作（如 ChromaDB 写入、Embedding、SSE 流）是否用生活化比喻解释？
- 一个完全不懂编程的人，读注释能理解这段代码在干什么吗？

**术语替换参考**：
| 技术术语 | 不好 | 好的写法 |
|----------|------|----------|
| `embedding` | 调用 embedding 模型对文本编码 | 把文字转换成一组数字（向量），让计算机能"理解"文字的含义 |
| `向量检索` | 使用 ChromaDB 做向量相似度检索 | 把问题也转成数字，去知识库里找"意思最接近"的几段文字 |
| `SSE 流式输出` | 使用 SSE 逐 token 推送 | 让答案像打字机一样一个字一个字地冒出来，不用等全部生成完 |
| `JWT` | 校验 JWT token | 校验用户的"通行证"，确认是本人登录后发的 |
| `BM25/RRF` | 用 RRF 融合 BM25 和向量分数 | 让"关键词匹配"和"意思相近"两种找法互相补充，综合打分排序 |

---

### 第三步：打分与评级

每个文件三个维度分别打分（1-5 分），然后给出综合评级：

```
📄 文件：backend/app/rag/chain.py
═══════════════════════════════════
📏 注释覆盖率：  ⭐⭐⭐☆☆  3/5  （注释率 22%，偏低）
✅ 注释准确性：  ⭐⭐⭐⭐☆  4/5  （1 处注释与实际代码不符）
👶 小白可读性：  ⭐⭐☆☆☆  2/5  （术语太多，新手看不懂）

📌 综合评级：🟡 需改进
```

**评级标准**：
| 总分 | 评级 | 含义 |
|------|------|------|
| 13-15 | 🟢 优秀 | 可以直接给小白看 |
| 9-12 | 🟡 需改进 | 部分地方需要补注释或改写 |
| 5-8 | 🔴 不合格 | 需要全面重写注释 |

### 第四步：生成改进清单

对每个问题，用表格列出修改建议：

```
🔧 改进清单
═══════════════════════════════════

问题 1（覆盖率）
📍 位置：第 45 行，build_context 函数
❌ 问题：函数缺少注释说明
✅ 建议：在函数前加 docstring：
  """
  把检索到的文档片段拼成给 LLM 的上下文
  :param docs_with_scores: 检索结果列表 [(文档, 分数), ...]
  :return: (上下文文本, 来源列表)
  """

问题 2（准确性）
📍 位置：第 78 行
❌ 注释写"取 Top-3"，但代码实际取了 Top-5
✅ 建议：修正注释为"取分数最高的 5 条"

问题 3（小白可读性）
📍 位置：第 120 行
❌ 注释"对 query 做 embedding 后查 ChromaDB"，新手看不懂
✅ 建议：改为"把问题也转成数字向量，去知识库里找意思最接近的几段文字"
```

### 第五步：汇总报告

全部文件检查完毕后，出一份总报告：

```

═══════════════════════════════════
📁 检查文件数：X 个
🟢 优秀：A 个
🟡 需改进：B 个
🔴 不合格：C 个

📏 平均注释率：XX%
✅ 注释准确问题：X 处
👶 小白可读性问题：X 处

📌 优先修复建议：
  1. [最紧急的问题]
  2. [其次]
  3. [...]
```

## 注意事项

### 什么算"注释"
- `#` 单行注释、`"""..."""` docstring（Python）
- `//` 单行注释、`/* */` 块注释、`/** */` JSDoc（TypeScript）
- HTML/Vue 模板中的 `<!-- -->` 注释

### 什么不算"注释"
- 被注释掉的代码（`# old_code = ...`）
- 空的注释行（只有 `#` 没有内容）
- 自动生成的代码中的模板注释（如 `# noqa`、`# type: ignore`）

### 沟通规范
- 用通俗语言解释每个问题，避免自己成为"术语轰炸机"
- 给出修改建议时，直接写出改后的注释文字
- 如果用户要求自动修复，用 Edit 工具逐个修改

### 项目约定
- 后端 Python（FastAPI + LangChain + SQLAlchemy），前端 Vue 3 + TypeScript
- 注释和界面文字都用中文
- 核心业务：RAG 检索增强问答（文档分块 → 向量化 → 混合检索 → LLM 生成）
